# Security test runner

The runner is intentionally constrained to the local lab. API-triggered tests
derive the listening port from the accepted backend connection and connect only
to `127.0.0.1`; the command-line runner uses `127.0.0.1:3000`. Test IDs are
allowlisted as `AT-01` through `AT-14`. The API accepts no target, URL, shell
command, username, payload, file path, or workload parameters.

## Run a test

From the repository root:

```powershell
npm --prefix backend run test:security -- AT-02
```

Only one test ID may be supplied. The backend dashboard has the same allowlist
and additionally requires an authenticated `security_admin` account. Reports
are written to `tests/reports/security/` as JSON and Markdown, with structured
evidence in `tests/reports/security/evidence/`. CLI reports link to that local
evidence file; API-triggered reports link to the authenticated evidence
endpoint. Reports contain no bearer tokens, passwords, private terms, or raw
response bodies.

Set `SECURITY_LAB_MODE=true` only for the isolated local lab. The Compose
backend receives this value from `.env`; the command-line script loads the
repository `.env` if present. If the flag is absent or false, runs are recorded
as `ERROR` without making test requests.

Tests that use a demo operator require `DEMO_USERS_PASSWORD` to be configured
for the backend process and the seeded local users to be active. AT-05 and
AT-06 require the local Fabric network. AT-08 and AT-09 require the fixed
SPEC fixture `YEN-2026-0001-A`. Missing prerequisites produce `ERROR`, never a
claimed pass.

AT-06 deliberately creates one uniquely prefixed append-only test batch so it
can verify replay behavior against real Fabric history. The record is not
deleted or rewritten. AT-05 only submits acceptance for a fixed nonexistent
shipment; AT-03, AT-04, AT-08, AT-09, and AT-13 are bounded reads or rejected
requests. AT-14 uses a separate ephemeral in-process app and eleven fixed
failed logins, so it cannot consume or lock out accounts on the running lab.

## Test catalog and limitations

| ID | Automated behavior | Scope limitation |
| --- | --- | --- |
| AT-01 | The authenticated dashboard checks six fixed TCP ports on the backend container's loopback. | The host CLI deliberately does not probe developer-machine ports; the test does not inventory the host, Fabric bridge, or LAN. |
| AT-02 | Missing and invalid bearer tokens. | Read-only. |
| AT-03 | Harvest role denied a processing-only endpoint. | API authorization boundary only. |
| AT-04 | Forged role/organization body fields rejected before Fabric. | Does not replace direct chaincode identity testing. |
| AT-05 | Real Fabric rejection for a fixed nonexistent shipment. | Does not exercise every invalid lifecycle transition. |
| AT-06 | Replays one event and checks Fabric history for one event. | Leaves one uniquely named test batch on the ledger. |
| AT-07 | The API runner returns `ERROR`; `blockchain/network/scripts/test-chaincode.sh` contains a real-peer endorsement check for an operator's isolated Fabric workspace. | The API does not launch host shell/Docker commands or submit that script's fixed transactions; no mocked endorsement result is accepted as evidence. |
| AT-08 | Non-member API denial and private-field inspection of public trace. | Does not issue a direct non-member PDC query. |
| AT-09 | Rejected update request plus before/after history comparison. | No direct ledger filesystem or volume tampering. |
| AT-10 | Read-only readiness check verifies Fabric Gateway connections succeed with configured TLS roots. | No packet capture; unavailable peers produce `ERROR` rather than a TLS claim. |
| AT-11 | Defined, but no scanner or Docker/container-control API is launched. | Run a separately approved offline scan and record image digest. |
| AT-12 | Defined, but no workload is generated by the API. | Requires an approved bounded profile and isolated lab. |
| AT-13 | One tiny invalid multipart upload is rejected before storage. | Does not upload a valid file or mutate ledger state. |
| AT-14 | Eleven failed logins in an isolated app instance. | Does not test or affect real accounts. |

`lab-current` records the configuration actually tested; it does not assert
that a hardened baseline has been independently certified. The hardened
profile is the repository's secure-by-default configuration. A baseline is
reference-only and must be captured from a reviewed, isolated snapshot; the
runner never toggles intentionally insecure settings. Baseline/hardened
comparison is unavailable until comparable reports have been captured.

No Phase 7 hardening or Phase 8 VMware deployment work is performed by this
runner.
